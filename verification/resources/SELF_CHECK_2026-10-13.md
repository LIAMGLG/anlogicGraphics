# FPGA 项目自检（2026-10-13）

## 结论

主视频采用四像素并行、整数运算、行缓存及流水线，整体符合 FPGA 的硬件实现方式。资源压力主要来自多个常驻功能、部分未共享的算术单元，以及存储映射，不能简单归因于“软件式写法”。主视频并行较充分；帧级检测主动采用串行处理节省资源，但存在分析忙时跳帧。模块职责基本清楚，接口协议、端口宽度和参数化约束需要进一步规范。

本次只做源码与实现报告审查，未改 RTL、约束、IP或用户的 Run 产物，未重新启动 TD、仿真或下载。以下区分已确认问题、结构性优化机会和需要进一步验证的风险。

## 1. 硬件资源是否存在浪费

### R1：卡通行缓存映射为分布式RAM，是优先优化候选

- 位置：`user_source/hdl_source/isp/cartoon_96.v:15,37,57`。
- 当前缓存为320×12 bit，异步读取 `color_line[current_x]`、时钟写入；综合层次报告实际为384个dram LUT、44个F7MUX、0 ERAM，另有130 logic LUT、48 ripple。
- 这是明确的映射成本，不是数组声明本身不合理。异步读结构不适合直接推断同步ERAM，仅修改 `ram_style` 不能保证有效转换。
- 建议改为明确同步读取的行缓存，并重新安排中心像素与Sobel掩码对齐。需保留读旧数据的行为，验证连续输入、行首行尾和SOF。可以评估ERAM换Slice，但没有新综合/布线证据前不承诺节省数值。
- `edge_detect_96`同样声明行缓存，但其层次报告为0 ERAM/0 dram LUT，表明映射结果与卡通不同；不能按源码容量猜测其资源成本，也不能把384个dram LUT归给Sobel。

### R2：轮廓状态机串行执行，但算术并未充分复用

- 位置：`isp/shape_contour_classifier.v` 的 `segment_area`、`DISTANCE_MULT`、`ANGLE_MULT`、`LINE_PRODUCT`、`ANGLE_TOLERANCE`。
- `u_contour`实际占1549 logic LUT、398 ripple、1231寄存器、2 ERAM、16 DSP；上层颜色形状检测整体为2358/478/2061、12 ERAM、17 DSP。
- 不同状态中书写独立的乘法表达式不等于共享一个乘法器。当前距离叉积、角点叉积/点积和多边形面积等表达式仍对应较多DSP。
- 建议按同时需要的运算数量设计共享乘法数据通路，明确操作数选择、符号扩展、结果寄存和状态调度。不要为节省DSP把所有乘法都转到LUT；本器件更紧缺的是Slice。
- 复用会增加MUX和周期。必须记录轮廓分析周期、CCL忙帧数、检测更新间隔，并与既有轮廓回归结果比较；仅DSP下降不等于整机更优。
- 已做得合理的部分：2048×17 bit轮廓点采用同步RAM；周长平方采用20拍移位累加；长度采用整数近似，避免平方根和宽除法。

### R3：MASK预览容量存在银行间空洞，但三银行具有功能必要性

- 位置：`isp/detection_mask_osd_rgb96.v:19`，`DEPTH=3*(1<<14)`，每字节存四个2-bit像素，实际综合21 ERAM、1 DSP。
- 每银行有效14400字节，却预留16384字节；三个银行实际声明393216 bit，有效数据345600 bit，声明容量利用率87.89%。硬块实际利用率还受器件RAM模式影响。
- 三银行分别保护采集、完成待提交、显示，直接删掉一个银行可能造成覆盖或撕裂，不应当作等价优化。
- 可以评估按实际深度紧凑映射或银行独立推断；须比较ERAM、地址译码和Slice的综合结果。当前Slice更紧，增加地址逻辑来省ERAM未必划算。
- 地址乘常量可能由综合器映射为移位加法或DSP，应以报告为准；不能见到 `*` 就认定为昂贵的通用乘法器。

### R4：模式切换不会释放硬件，关闭叠加也不会停止检测

- 位置：`isp/isp_top.v:178`附近及 `processed_data`输出选择；颜色检测始终从AWB分支运行。
- NORMAL/BINARY/SOBEL/CARTOON/GRAY/MOTION的硬件在bitstream中常驻。运行时只选择输出，属于可即时切换的正常设计成本。
- MOTION之外，运动核通过enable停止有效处理；红绿检测在MOTION和关闭叠加时继续运行，是现有行为要求。
- 如需降低功耗可增加clock enable，但不能声称这样降低已实例化资源。只有编译期关闭功能或共享数据通路才可能减少硬件；这些选择要先明确是否保留当前功能。

### R5：基础AWB占用大，但不作为本次优先改造对象

- 实际AWB入口是 `user_source/hdl_source/awb.v`，不是备份目录的同名文件。
- 层次报告：AWB 1533 logic LUT、2306 ripple、6086寄存器、10 ERAM、8 DSP；两个除法器各640 logic LUT、1084 ripple。
- 除法器随有效像素拍启动，处理的是持续变化的累积通道比值；把它替换为每帧一次除法会改变算法、更新时点和延迟，并非等价压缩。
- 优化基础AWB有潜力，但沿用现有交接约定，优先改进新增显示、检测和诊断模块。不能为了资源数据好看而直接删除必要模块。

## 2. FPGA并行执行是否充分利用

### 已合理使用

1. 四个RGB888像素每拍处理，增益、饱和度、灰度和OSD的固定循环展开为并行电路，不是CPU式循环执行。
2. Sobel每拍计算两个窗口，结果分别复制给两像素；这利用了并行硬件，同时以水平精度换资源，不能声称是四个独立全分辨率Sobel结果。
3. 显示、红绿检测和运动检测有独立数据分支，检测不向主视频施加背压。
4. 卡通复用Sobel边缘掩码，避免重新实例化边缘核。四像素共用同一字符行、共用纵向框判断，也属于合理复用。
5. 八个坐标共享一个BCD转换器，SOF后104拍完成，远早于坐标面板显示位置。低频控制使用串行运算合适，无需并行展开八套转换器。
6. 检测框和使能在SOF快照，降低帧内变化导致撕裂的风险。

### 检测并行度受限，属于资源与更新率的权衡

- `color_shape_detect.v:94`仅在IDLE时接受新帧，单掩码RAM在采集和分析之间互斥；分析忙时整帧跳过。
- CCL逐像素多状态处理，逐行规范化标签、查根、回收；四个候选复用同一轮廓核串行分析。它不能自动保证每个60fps输入帧均有检测结果。
- 并行化候选轮廓或增加双缓冲能提高吞吐，但会增加DSP、ERAM、控制逻辑。现有95.13% Slice占用下，不建议直接复制整套检测核。
- 先测量采集/分析周期和忙帧数。若更新率不足，优先考虑同步RAM访问流水化、减少非必要等待，以及允许下一帧采集与上一帧分析重叠；必须保护正在分析的掩码。
- `target_tracker`顺序扫描4×4配对、使用宽动态选择器。较低更新频率下串行匹配合理；宽MUX是可评估的结构成本，不能仅因为705 logic LUT就认定算法错误。

### 最新报告提供了具体时序优化方向

- MIPI域最紧Setup路径：`u_mode_osd/x_reg[11] → u_mode_osd/O_tdata_reg[36]`，+0.136 ns。当前一拍内组合完成面板判断、字符选择、字形查找和像素选择。
- 优先评估预译码或流水分段，而不是继续堆组合逻辑。增加流水拍必须同步data/valid/SOF/last/模式及延迟观察点。
- DDR域全局最差Setup路径：命令FIFO读地址进入 `u_latency/u_slots/words`计数器CE，+0.114 ns。相关逻辑含slot地址译码、动态计数选择、期望地址比较和计数更新。
- 可评估按槽独立局部比较/使能或寄存译码；若寄存提交事件，必须同时延迟地址与相关元数据，保持对真实DDR写命令的计数语义。
- 本次Setup/Hold通过，但裕量小；优化不能只追求资源数量，也要关注MUX、扇出和组合级数。

## 3. 模块规范、端口命名与复用

### I1（高优先级）：ready未驱动，且接口不支持完整背压

- `design_top_wrapper.v:91,719`声明并连接 `S_ISP_O_tready`，未找到驱动；最新综合日志明确警告 `u_isp_top/O_tready` 未驱动，并声明未驱动网络按0处理。
- `isp_top.v:11,16`使用input `O_tready`、output `I_tready`；AWB和Sobel透传ready，但视频寄存器仍每拍更新，未实现stall时保持数据。
- 这种命名源于输入侧/输出侧接口习惯，但与全工程I_/O_方向前缀冲突，容易误接。
- 建议明确此链路是不可停顿的视频流。若需要保留ready兼容端口，应给出确定值并记录限制；单纯绑1只消除悬空，不会补齐AXI握手。
- 若要支持AXI Stream背压，必须逐级实现 `valid && ready`传输、输出保持与必要缓冲，不能只透传ready；摄像头源不能任意暂停，入口仍需溢出策略。

### I2（高优先级）：打包器依赖连续valid，复位和last接口不完整

- `data_96bit_to_128bit.v:30`在valid为0时清零 `S_cnt`，并仅保存前一时钟输入的数据。因此行内空拍会丢失已积累的部分数据，不适合作为通用流宽转换器。
- 对连续四个96-bit输入拍，三个128-bit输出是正确的节奏；720p每行320个输入拍能整除4。当前AWB输出按连续行组织，现有使用有其前提。
- 本次用PowerShell复核计数状态转移：8个连续有效拍在第1/2/3/5/6/7拍产生输出；8个有效拍各插入一个空拍时产生0个输出。该复核不是RTL仿真，但与源码状态更新一致。
- `I_rst_n`声明后未使用。若复位期间输入valid未及时清零，模块不能保证确定的初始相位；不能依赖复位输入端口名称就认为复位已实现。
- `isp_top.v:90`将128-bit输出的 `O_tlast`直接接 `logo_last`，没有经过打包器同级寄存或重新生成。它不属于与128-bit输出同步的完整行末接口。当前顶层只把该信号接到内部线/注释掉的探针，DDR写入不使用它，因此是潜在复用缺陷，不能认定为当前画面异常根因。
- 建议定义行内连续输入契约，或改成按有效拍积累且空拍保持的转换器；补齐复位，并明确SOF可提前、last是否与最终有效输出同拍。新增用例应覆盖空拍、首拍、行末、帧切换和中途复位。

### I3（中优先级）：手写模块边界存在宽度告警

| 位置 | 当前情况 | 影响与建议 |
|---|---|---|
| `design_top_wrapper.v:600` | 4-bit `I_lane_invert`接2-bit端口 | 当前全0截断不改变数值，改为匹配lane参数的位宽 |
| `raw_matrix_3x3_buffer.v:149` | `.O_raw_tready(1)`为32-bit常量接1-bit | 改为 `1'b1`，避免依赖隐式截断 |

生成IP还有未连接位、宽度和加密DDR内部latch告警；这些告警不能统一归为用户RTL缺陷，也不能未经核对全部忽略。优先清理可控的手写边界，不直接修改厂商加密或生成逻辑。

### I4（中优先级）：参数化接口与固定布局混用

- 运动模块虽暴露IMG_WIDTH/IMG_HEIGHT，却固定输出144区域、16列、部分坐标和地址位宽；跟踪 `STABLE_UPDATES`等参数与固定3-bit/8-bit计数器也存在范围约束。
- 当前1280×720默认值匹配实现，不能因此判为当前功能错误；但更改参数并不能自动迁移分辨率或容量。
- 建议用localparam统一位宽、区域数和分辨率，或明确限制参数并增加非法配置检查。不要宣传模块可接受任意分辨率。
- 模式3'd0～3'd5、64-bit目标记录字段散布多个模块。推荐统一常量和字段定义，保持现有Verilog工具兼容性；使用记录访问函数减少重复魔数。
- `O_ready`在运动核表示参考/结果就绪，与AXI接收ready含义不同；建议改为 `O_reference_valid`或明确文档。`I_key_bin`已经控制六模式，建议改为 `I_key_mode`。

### I5（中优先级）：时钟与复位需要硬件级规范复核

- 顶层 `S_rst_n=S_pll_lock`直接分发多个时钟域，未见顶层统一的各域同步释放结构。建议核查各IP内部复位机制，按域设计异步断言、同步释放；不是在所有位置机械新增两拍。
- I2C `uii2c.v`把逻辑产生的 `scl_clk`用作posedge/negedge时钟，最新报告确有该网络时钟/数据混合扇出告警。可评估改为单I_clk域的边沿使能状态机，保留SCL/SDA时序及开漏控制。
- 最新报告还包含摄像头24MHz网络混合扇出、1个时钟网络使用局部布线的critical warning。局部布线网络的身份需详细时钟报告确认，不能未经证据断言就是I2C时钟，也不能把所有混合扇出都判为故障。
- 延迟CDC使用稳定负载邮箱及双级toggle同步，结构合理；两条req1/ack1入口例外仍存在。本次日志检索未见对象未匹配告警，但这不等同于完成数据库对象及所有CDC路径复核。修改相关层级、复位或延迟时必须保留并复核入口例外、第二级路径和负载稳定时间。

### I6（低优先级）：源码副本影响维护，不等于资源重复实例化

- 源树存在同名 `awb`、`signal_delay`、`uial2axis`旧副本；当前工程使用根目录AWB、根目录signal_delay和isp目录uial2axis。
- 基于TD工程直接列出的63个启用Verilog文件，提取模块声明未发现同名重复；此检查不包含加密IP内部展开，不能声称检查了所有定义。
- 未入工程或未实例化的旧文件不会自动增加硬件资源，但容易误改，通配导入后也可能冲突。
- 建议归档旧副本、说明有效入口；保留专用RGB96并行模块，不强行把所有像素、元数据和CDC都变成一个通用模块。

## 推荐处理顺序及验收

1. 先补齐接口契约：悬空ready、打包器reset/valid空拍约束、last对齐、手写端口位宽。验收确定行为，不仅消除警告。
2. 再做保留功能的Slice优化：同步ERAM卡通缓存，模式OSD预译码/流水分段，延迟计数译码优化。分别比较资源和时序，避免同时大改导致难以定位。
3. 根据检测更新率再决定轮廓算术共享、CCL流水及缓冲重叠。保持轮廓容量、目标数、分类规则和输出稳定策略。
4. 改动相关模块后运行已有模式、卡通、Logo、运动、形状/跟踪和延迟回归；补充接口空拍及复位场景。真实AWB、DDR和HDMI仍需完整实现与实板验证，ISP替身仿真不能代替。
5. 用户重新Run后保存源码、约束、bit哈希与报告对应关系，检查最终资源、Setup/Hold、时钟告警和CDC入口例外。以最新构建为准，不沿用历史正裕量。

本次最终判断：硬件架构方向正确，主视频并行充分；资源复用和接口规范仍需改进。最新实现时序通过，但95.13%的Slice占用与较小裕量使保留功能的资源/时序优化具有实际必要性。
